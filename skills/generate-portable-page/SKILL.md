---
name: generate-portable-page
description: Create generic Page visualizations with complete portable HTML sources for this project's compact v3 pairing format, retaining v2 compatibility.
---

Generate content according to this repository's `docs/format.md` and the [English authoring format reference](../gpt-pages-obsidian-visualizations/references/export-format.md). v3 and v2 are this project's pairing declarations, not a guarantee that every Pages export format can be restored.

1. Author generic content without private Pages, course materials, exports, account identifiers or local paths. Use the user's requested language for Page content.
2. Create real native visualizations in the Page, each with an adjacent, stable figure ID unique within the document. A literal `visualize:` reference is not evidence that a visualization was created.
3. Include complete fenced `html` for each figure: doctype, html/head/body, UTF-8 metadata, CSS, JavaScript and all data. Prefer self-contained sources and disclose every external asset. Include one static and one interactive example; the interactive example needs a slider and reset control.
4. Preserve the exact HTML source before creating the real native visualization and obtain the file ID returned by the tool. Do not substitute a Page ID, filename, guessed ID or a literal `visualize:` reference.
5. Use `node scripts/figure-marker.mjs --v3 FIGURE_ID NATIVE_FILE_ID SOURCE.html` to generate the body and footer markers. The HTML file must end with a newline. The digest covers the complete UTF-8 source bytes, including the final newline, BOM and CRLF. Use the same unchanged source for uploading, fencing and hashing; do not reformat it. Omitting `--v3` still produces the legacy v2 marker.
6. Use separate top-level blocks for each pair. For new Pages, place only `<!-- gpt-pages:figure id=example-chart -->` in the body, followed by the real image-style `![title](visualize:file-id)` embed. Collect complete HTML at the bottom, with `<!-- gpt-pages:source v=3 id=example-chart ref=ACTUAL_NATIVE_FILE_ID sha256=ACTUAL_64_LOWERCASE_HEX -->` before each fence. Separate the source marker and fence only with blank lines. Do not add source-section headings or instructions. Figure IDs, source IDs and native file IDs must each be unique; pair body and footer with the same ID. Older adjacent and footer v2 layouts remain supported; do not mix versions.
7. Put `ref` and SHA-256 only in the v3 footer source marker. `ref` excludes the `visualize:` prefix. Pages' CommonMark escaping can change the textual representation of markers and references; do not globally decode the export afterward. If exported HTML bytes change, preserve the references and investigate/correct the source rather than simply recalculating the digest to conceal the difference.
8. Do not globally decode escaping or remove backslashes. If source contains a fence delimiter, use a longer enclosing delimiter.
9. Checksums confirm declared pairings, not source safety or a digital signature. Previews must not execute HTML/JavaScript. Verified pairing does not automatically enable a renderer; explicit user trust is still required.
10. Use fictional identifiers in public examples, fixtures and skills. Keep actual UI exports, Page URLs, attachment/upload/block IDs, service receipts and original screenshots outside Git. Publish only summaries without source identifiers. Record differences between the export and working copies, the date, renderer/Obsidian/OS/view mode and results. Run `npm run check:public` and explicitly label mobile behavior as untested when applicable.
